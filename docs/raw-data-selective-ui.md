# raw_data 청크 및 관리자 선택적 복원 검증

## 최종 구조

운영 녹화는 프로젝트 루트의 `raw_data`만 사용한다.

```text
raw_data/
  .keys/{external,internal,master}.key
  YYYY-MM-DD/HH/HH-MM-SS/
    protected.avi
    external.gcm
    internal.gcm
    master.gcm
    manifest.json
  .results/<작업ID>/
```

기존 `data` 폴더는 삭제·이동하지 않았다. 업그레이드 시 기존 세 운영 키를 한 번 읽어 `raw_data/.keys`로 복사해 권한 연속성을 유지할 수 있지만, 기존 `data`의 청크는 신규 저장·목록·복원 입력에서 읽지 않는다. 실제 장시간 시험 전후 파일 목록·크기·mtime 지문이 같아 `data_unchanged=true`였다.

`config.py`의 `CHUNK_SECONDS=60`을 시작 시 검사한다. monotonic 경과 60초가 되면 암호화 메모리 버퍼를 확정하며 시스템 시계 변경은 분할 기준에 영향을 주지 않는다. KST 시작 시각이 폴더와 manifest에 들어간다. `.HH-MM-SS.partial`에서 영상 왕복 검사, 암호문·manifest 쓰기, fsync를 마친 후 최종 폴더로 원자 rename한다. 충돌은 덮어쓰지 않고 오류로 남긴다. 종료 시 60초 미만 버퍼는 폐기한다. 실패 주입 테스트에서 `.partial`은 완료 인덱스에 나타나지 않았다.

## UI와 인증

관제 화면의 공용 상단 메뉴는 `실시간 모니터링 | 보호 자산 | 관리자`이며 `과거 영상 복원`을 제거했다. 관리자 메뉴의 `원본 복원`과 `선택적 복원`은 유지한다. 비관리자의 두 복원 페이지/API 접근은 기존 `admin_session`으로 차단한다.

선택적 복원 화면은 관리자 헤더와 메뉴 아래 좌우 패널로 구성한다. 왼쪽은 완료 청크를 최신순으로 보여주고, 오른쪽은 시간·길이·프레임·FPS·해상도·집단별 영역 수·상대 경로·보호 프레임을 표시한다. 녹화 시작 버튼과 실시간 카메라 화면은 없다. 외부인키·내부인키·전체키 카드 중 하나와 32바이트 키 파일을 선택해야 실행된다.

선택 역할은 요청 헤더의 공개 식별자일 뿐 권한이 아니다. 서버는 해당 manifest envelope의 AES Key Wrap을 실제 제출 바이트로 풀어 역할과 일치하는지 먼저 확인한다. 파일명은 보지 않는다. 불일치·난수 키는 403이며 작업/부분 결과를 만들지 않는다. 이후 worker가 전체 manifest, GCM, 영상 해시를 다시 검증한다. 성공/실패와 안전한 청크 UUID는 기존 감사 로그에 기록하고 키 값·절대 경로는 기록하지 않는다.

보호 자산의 누락 필드는 `-` 또는 `계산 중`으로 표시한다. 실제 Chromium에서 본문에 `undefined`가 없고 보호 프레임, 결과 프레임 재생, AVI 다운로드가 작동함을 확인했다.

## 실제 Logitech 시험

실행 명령:

```bash
source hk_env/bin/activate
CAMERA_DEVICE=/dev/video0 python main.py
```

설정은 `CHUNK_SECONDS=60`, 목표 `SELECTIVE_FPS=10`이었다. Logitech MJPG 640×480 입력과 실제 SCRFD/ArcFace 처리를 함께 수행했다. 처리량이 목표보다 낮은 차이는 드롭으로 기록했고, 컨테이너 FPS를 `저장 프레임/60초`로 정해 실제 재생 길이를 유지했다.

| 경로 | ffprobe 길이 | 프레임 | 저장 FPS | 드롭 |
|---|---:|---:|---:|---:|
| `raw_data/2026-09-16/21/21-30-39` | 60.000000초 | 462 | 7.70 | 138 |
| `raw_data/2026-09-16/21/21-31-52` | 60.002586초 | 464 | 7.7333 | 136 |
| `raw_data/2026-09-16/21/21-34-11` | 59.997391초 | 460 | 7.667 | 140 |
| `raw_data/2026-09-16/21/21-35-36` | 59.996238초 | 319 | 5.317 | 281 |

뒤 두 청크는 세 키와 브라우저 결과 생성 중 CPU 경쟁이 있던 구간이다. `21-36-49`로 시작한 다음 버퍼는 서버 종료 시 60초 미만이어서 완료 폴더로 게시되지 않았다. 재시작 후 네 완료 청크가 다시 조회됐고 카메라를 재개방했다.

터미널 완료 로그 예:

```text
[CHUNK] 저장 완료 | 시작=2026-09-16 21:34:11 KST | 종료=2026-09-16 21:35:36 KST | 경로=2026-09-16/21/21-34-11 | 목표=60초 | 길이=60.00초 | 프레임=460 | FPS=7.67 | 드롭=140 | 크기=81.5MB
```

`종료`는 이 시험 로그에서 파일 확정 시각이며 manifest의 촬영 종료는 시작+60초다. 최신 로그 형식은 `촬영종료`와 `저장완료`를 별도 필드로 출력하며 manifest의 `ended_at`은 촬영 종료 시각이다. 위 로그는 수정 직전 실제 장시간 실행 기록이어서 `종료`가 파일 확정 시각이다.

동일한 `21-31-52` 청크에서 서버 API로 다음을 검증했다.

- 외부인키 → `external` 권한만 확인, 464프레임 결과·다운로드 생성.
- 내부인키 → `internal` 권한만 확인, 464프레임 결과·다운로드 생성.
- 전체키 → `external`, `internal`, `master` 권한 확인, 464프레임 결과·다운로드 생성.
- 외부인키를 전체키로 선언하거나 난수 키 제출 → 403.
- 관리자 UI에서 외부인키를 제출해 결과 프레임 재생과 AVI 다운로드 성공.

이 실제 두 청크의 장면에는 검출된 얼굴이 없었다. 따라서 키 검증과 전체 영상 결과 생성은 실장비로 확인했지만, 이 청크에서 집단별 얼굴 픽셀 차이는 관측하지 못했다. bbox padding 0은 단위/암호화 회귀에서 `write_roi == bbox`, 마스크 합집합이 bbox 합집합과 동일하고 bbox 밖 픽셀이 원본과 같은 것으로 검증했다. 이전 Logitech 실물 얼굴 시험의 강한 블러·허가/비허가 표시는 유지되지만, 최신 장면으로 얼굴 범위를 다시 실측했다고 주장하지 않는다.

## 검증 결과와 파일

- 단위·보안 회귀: `60 passed`.
- 기존 main.py 브라우저·외부/내부/전체키·변조·과거 AES 회귀: 성공.
- 장시간 실장비 JSON: `tests/runtime/raw-chunk-verification/report.json`.
- UI 화면: `tests/runtime/raw-chunk-verification/selective-ui.png`.
- 터미널 로그: `tests/runtime/raw-chunk-verification/main.log`.
- 브라우저 다운로드: `tests/runtime/raw-chunk-verification/browser-restored.avi`.

Raspberry Pi/RealSense 실장비, 장시간 연속 운용, 이번 최신 청크의 실물 얼굴 bbox 비교는 미검증이다. Logitech MJPG의 extraneous bytes 경고는 일부 남았지만 프레임 수신과 청크 무결성 검사는 통과했다.
